Architecture overview

One shared payments-api service (its own DB = payments_v2) serves every Salam surface. Each surface authenticates with its own API key = one row in applications, and receives status callbacks on its own webhook_url.

Click a node to trace its connections, or a flow chip to isolate one path. Click again / “All” to reset.
The load-bearing fact: the BSS order is placed by the webhook callback (notifyApplication → /webhooks/…/payment), not by the browser poll. The front-end checkPayment poll only drives the UI and the PAID_BY_ZERO short-circuit. If the callback fails, money is captured but no service is provisioned.

Multi-tenant applications model

payments-api is multi-tenant. The three tRPC clients in packages/api/src/clients/payments.ts each carry a different x-api-key → resolve to a different applications row → different webhook_url + webhook_secret. This is how one payment engine fans back out to the correct journey.

Web QR code journey

The "QR Code" journey is not a separate payment rail. A QR carries a referralCode (stored in localStorage/sessionStorage, read in components/stepper.tsx). When present with a QR-enabled plan (enableQrOfferPrice), the customer is charged qr_discounted_price instead of the standard price. Everything downstream (invoice → Moyasar → webhook → BSS) is identical to the web card flow.

Click a node or a branch chip (yes / no) to trace the QR pricing decision.
Test implication: QR only changes the amount on the invoice. The amount-match guard in handleWebhook (invoice.amount !== payment.amount) means a mispriced QR invoice will silently fail to progress — a good negative test.

Apple Pay / Samsung Pay / STC Pay

Wallet rails differ in how the token is obtained, then converge on the same invoice/webhook machinery.

Apple Pay
Browser runs applepay/initiate (merchant validation) → gets a wallet token → POSTs to Moyasar source.type=applepay with manual from paymentFlow. Same /webhooks/moyasar path.
Samsung Pay
Server-side: SamsungPayment mutation → moyasar.createSamsungPayment(invoice, token). Only paid/authorized/captured return a payment; a payment row is created immediately with source=SAMSUNG_PAY.
STC Pay (via Tap)
initTapStcPayment → Tap charge INITIATED → OTP → confirmTapStcOtp must return CAPTURED. Channel TAP_PAYMENTS, source STC_PAY.

Pulse mobile — buy FTTH + manage-line

Pulse hosts two distinct payment journeys against two different applications.

A. Buy FTTH (ePurchaseFTTH, paymentClient → /webhooks/epurchase/payment)

Identical engine to web e-purchase: MANUAL_CAPTURE invoice, direct Moyasar call from the app (apps/pulse/src/lib/moyasar.ts), checkPayment poll @5s, webhook-driven createOrderNew, capture-on-success / void-on-failure.

B. Manage-line (salamHomePaymentClient → /webhooks/salamHome/payment)

Relocation / change-plan / renew. Invoice must reach PAID; the callback routes by metadata.serviceType.

SDA dealer — SADAD instant invoice

Dealers (SDA app) sell FTTH/FTTB/5G. Payment is collected via a SADAD instant bill: BSS generateInstantInvoice(serviceId) returns a sadadAuNumber + charge; a payments-api invoice is created (paymentOptimizationClient) carrying the SADAD reference in metadata. The customer pays the SADAD bill through their banking app; once the invoice becomes PAID, payments-api calls /webhooks/sadad/payment.

The customer pays out-of-band (bank / SADAD) — no inline card. Click an actor, a flow chip, or step through with ◀ Prev / Next ▶.
The SDA callback runs a retry wrapper (3 attempts, attempt × 10s backoff) around sadadPayment and increments webhook_requests.retries. This is the exact endpoint (172.31.38.146:3056/sda/webhooks/sadad/payment) that appeared in the "paid but not notified" incident — a 12s notifyApplication timeout on the payments-api side means the retry loop here never even starts.

App-notify & BSS order placement

notifyApplication (payments-api) is the bridge from "money moved" to "service provisioned". It is a single POST with a 12-second timeout and no retry loop inside payments-api — success sets webhooks.status=DELIVERED + notifiedAt; failure sets webhooks.status=FAILED and stops.

SADAD notification flow (detail)

SADAD is a Saudi bill-payment rail, distinct from card. In payments_v2 it shows up as invoice.sadad_id, payment_channel=SADAD, payment_method=SADAD, payment_source=SADAD. The customer pays a SADAD bill number in their banking app; the resulting invoice-PAID event drives the same notifyApplication → /webhooks/sadad/payment callback.

FieldMeaning
metadata.customerIdBSS customer
metadata.orderNumber / sadadReferenceorder + SADAD AU reference
metadata.amount / totalAmountpaid vs full (drives remainingAmount → realTimeBillUpload)
metadata.sadadInvoiceIdSADAD AU number for bill upload
Partial payment handling: remainingAmount = amount==totalAmount ? 0 : totalAmount − amount → realTimeBillUpload(sadadInvoiceId, remainingAmount) pushes the residual back as a prepaid bill. Worth an explicit test: full-pay (remaining=0) vs partial-pay (remaining>0).
The ingress that flips a SADAD invoice to PAID inside payments-api is the payment-provider boundary and is not in the core routers reviewed — treat "SADAD bill paid → invoice PAID" as the trust boundary to stub in E2E.

Failure & defect cases

The high-value negative paths — several are live production defects surfaced in the payments-api winston logs.

8SADAD callback failurewebhook_requests.isSuccess=falsesadadPayment fails all 3 retries → paid, no BSS provisioninghigh
The systemic risk across cases 2 & 8: payments-api considers its job done once notifyApplication returns/fails; the money is captured but provisioning is fire-and-forget with a short timeout. The reconciliation must be driven off webhooks.status = FAILED and webhook_requests.isSuccess = false.

Test coverage hooks (Maestro E2E + integration)

Mapping the flows above to concrete, testable branches.

Happy paths (one per surface)

  • Web card: createInvoice(MANUAL_CAPTURE) → Moyasar authorized → webhook → BSS order → capture → invoice CAPTURED.
  • Web QR: referral present → invoice amount = qr_discounted_price → same as web card. Assert charged amount.
  • Pulse buy: ePurchaseFTTH poll @5s until PAID/CAPTURED; assert orderNbr.
  • Pulse manage: PAID_BY_ZERO short-circuit (charge 0) and paid path per serviceType.
  • SDA SADAD: generateInstantInvoice → invoice PAID → sadadPayment success → webhook_requests.isSuccess.

Status-driven branches (drive via Moyasar test-mode / stubbed /webhooks/moyasar)

  • Each of paid / authorized / captured / voided → assert invoice transition + webhook_type + DELIVERED.
  • failed / refunded / verified → assert NO invoice change, NO app notify (documents current behavior / potential bug).
  • Idempotency: replay same webhook → "already X", no double order.
  • Guards: amount mismatch, version≠2, expired invoice, invalid transition.

Defect regression

  • P2002: fire duplicate webhook + initPayment concurrently → expect graceful handling, not 500.
  • Notify timeout: make webhook_url hang >12s → webhooks.status FAILED → reconciliation picks it up.
